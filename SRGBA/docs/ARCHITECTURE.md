# SRGBA Architecture

## Design goals

1. Keep emulated hardware deterministic and independent of host APIs.
2. Model timing from the first CPU implementation instead of assuming one cycle per instruction.
3. Make every hardware block testable without opening a window.
4. Serialize logical state explicitly; never save raw C++ object memory.
5. Keep the first implementation understandable before pursuing JIT compilation or heavy
   optimization.

## Runtime boundary

The desktop frontend owns SDL, Dear ImGui, host input, audio devices, file dialogs, frame pacing,
and presentation. The core owns the cartridge, ARM7TDMI state, GBA bus, scheduling, PPU, APU, DMA,
timers, keypad registers, interrupts, and future save-state serialization.

The intended frontend/core exchange is deliberately small:

- Load or unload cartridge and BIOS bytes
- Reset or advance the machine
- Set GBA key states
- Read a completed 240x160 RGBA framebuffer
- Drain generated stereo audio samples
- Serialize or deserialize versioned machine state

No core header may include SDL or Dear ImGui headers.

## Planned timing model

The GBA master clock is 2^24 Hz. A central scheduler will track the next event for the PPU, DMA,
timers, audio FIFOs, and interrupts. Each ARM or Thumb instruction will perform bus accesses and
return the cycles consumed, including sequential/non-sequential access timing and pipeline refill
costs. The scheduler then advances hardware to the new master timestamp.

The first implementation will be an interpreter. A decoded-instruction cache or JIT can be
considered only after the interpreter passes instruction and timing tests.

## M1 CPU boundary

`Arm7Tdmi` now owns the physical register banks, CPSR, SPSRs, ARM/Thumb execution state, exception
entry, and the first instruction decoders. Its stored r15 value is the current fetch address;
operand reads apply the ARM7TDMI pipeline offset, while branch results report that the pipeline
must be refilled. Unsupported instruction classes leave state unchanged so later milestones can
add memory, multiply, and transfer decoders without treating missing implementation as hardware
behavior.

## M2 bus and boot boundary

`GbaBus` owns all writable memory in the GBA address map and holds non-owning access to the active
cartridge bytes. BIOS bytes are separately owned by the bus so unloading a cartridge never removes
a user-selected BIOS. Reset clears volatile memory and IO but preserves both attached images.

Bus reads and writes return the master cycles consumed. Internal regions use their documented bus
widths, while Game Pak accesses distinguish WAITCNT-selected first and second access timing,
32-bit transfers on the 16-bit cartridge bus, and forced non-sequential timing at 128 KiB
boundaries. The WAITCNT prefetch-enable bit is retained, but the eight-halfword prefetch queue will
be connected to the M3 scheduler rather than approximated without instruction timing.

`Arm7Tdmi::step` fetches through the bus and dispatches to the same instruction executors used by
isolated vectors. ARM single/halfword/block transfers and Thumb formats 6-15 now use bus accesses;
branch or PC-load results force the following opcode fetch to be non-sequential. Unsupported
encodings pause the high-level emulator instead of silently advancing through unknown code.

Two reset paths are available:

- BIOS boot starts in masked ARM Supervisor mode at `0x00000000` when a validated 16 KiB image is
  loaded.
- Direct boot initializes the user, IRQ, and Supervisor stack banks, minimal post-BIOS IO state,
  and ARM System mode before starting the cartridge at `0x08000000`.

The M2 integration ROM is generated by the tests from original ARM instruction words; no ROM or
BIOS binary is committed to the repository.

## M3 scheduling, interrupts, and video boundary

`Scheduler` keeps one deadline per hardware event type on the master clock. Events fire in deadline
order (ties resolve by event-type order), handlers reschedule from the event's exact timestamp so
timing never drifts, and the fixed-size state is straightforward to serialize for save states.
`Emulator::step_instruction` executes one CPU instruction (or, while halted, skips straight to the
next event), dispatches due events, then services interrupts. Frames end at multiples of 280,896
cycles, aligned with the start of scanline 0.

`Ppu` owns VCOUNT and the DISPSTAT status bits. Each line raises HBlank 1,006 cycles after it
starts and ends after 1,232 cycles; line 160 starts VBlank. The visible line is rendered into the
framebuffer at HBlank. M3 renders forced blank, the backdrop, and bitmap modes 3-5 with identity
BG2 transformation; tile modes and affine parameters arrive in M4.

`GbaBus` implements IE, IF (write-one-to-clear), IME, HALTCNT, KEYINPUT, and KEYCNT. Any enabled
request wakes a halted CPU; the IRQ exception is taken only when IME is set and CPSR.I is clear.

When no user BIOS is loaded, the BIOS region holds SRGBA's own small system ROM
(`system_bios.cpp`): exception vectors, the standard IRQ dispatcher (which calls the handler at
`0x03007FFC`), and an IntrWait loop that halts in System mode with IRQs enabled. When execution
reaches the SWI vector, `HleBios` reads the call number from the caller's instruction and performs
the service in C++, returning with `MOVS pc, lr` semantics. IntrWait/VBlankIntrWait continue in the
system ROM wait loop so interrupts are delivered exactly as they would be on hardware.

The demo ROM in `tools/homebrew` is assembled from C++ by a small ARM assembler. Tests run it end
to end, and the build writes it to `samples/SRGBA-demo.gba` for release packages.

## Planned core modules

```text
Emulator
├── Scheduler
├── Arm7Tdmi
│   ├── ARM decoder/executor
│   ├── Thumb decoder/executor
│   ├── banked registers
│   └── exceptions and pipeline
├── Bus
│   ├── BIOS, EWRAM, IWRAM
│   ├── IO registers
│   ├── palette RAM, VRAM, OAM
│   └── Game Pak ROM and backup media
├── PPU
├── APU
├── DMA
├── Timers
├── Interrupt controller
└── Keypad
```

## Persistence rules

- Battery saves will be keyed by ROM identity and written through a temporary file.
- Save states will start with a magic value, schema version, ROM hash, and component sections.
- Unsupported future state versions must fail cleanly rather than partially loading.
- Frontend settings are not part of an emulated save state.

## Testing strategy

- Unit tests: decoding, barrel shifter, ALU flags, bank switching, memory mirroring, register masks
- Instruction vectors: ARM and Thumb result/flag comparisons
- Hardware test ROMs: public and redistributable suites only
- PPU regression tests: deterministic framebuffer hashes and selected reference images
- Integration tests: homebrew boot, input, DMA, timers, interrupts, and cartridge saves
- Sanitizer jobs: core-only builds where supported

## Clean-room rule

Specifications, public research, and test behavior may guide implementation. Do not paste or
translate implementation code from another emulator. Code from GPL emulators is not compatible
with SRGBA's MIT license unless the project's licensing strategy is deliberately changed first.
